Phantom Go · as-is architecture

How this codebase is put together

A Rust game server and a plain-JavaScript browser client, about 6,800 lines in total. The diagrams follow the C4 model: each one zooms in one level further, and each is meant to be understandable on its own. Everything up to section 10 describes the code as it exists today. Sections 11 onward propose changes.

1 · Words you need first

Phantom Go
Go, but each player is not supposed to see the opponent's stones. You learn where they are by playing into them and being told the move was rejected.
Match string
The text a player types on the join page. It is the primary key for a game — every server-side map is keyed by it. Any string works; typing an existing one joins that game.
Seat
The black slot or the white slot in a game room. A room has exactly two. Anyone who arrives after both are filled becomes a spectator.
Session token
A UUID the server mints when it gives you a seat. Stored in the browser's localStorage. It is the only credential in the system — whoever holds it owns that seat.
Generation number
A counter on the room, bumped on every change. The browser keeps its own copy and asks the server "is yours higher than mine?" to decide whether to refetch. Called game_generation_number on the server and boardGenerationNumber in the browser.
Sentinel border
The rules engine stores the board with one extra ring of Invalid cells around the edge, so neighbour-checking code never has to test for "am I off the board?". It makes internal coordinates one larger than real ones.
Guess stone
A marker a player places on their own board to record where they think an opponent stone is. It is a private annotation, not a move.
Atari
A group of stones with only one liberty left — one more opponent move captures it. The server tells each player how many of their own stones are in atari.
SGF
Smart Game Format, the standard text file format for a recorded Go game. The server can export one for any match.

2 · System context

The admin routes have no password. The three admin endpoints accept any request. admin.js carries the author's own note: // TODO: investigate how to make this panel password protected. Treat it as a known open item, not a discovery.

3 · Containers

The Rust program embeds the whole frontend/ folder into its own binary at compile time, so in principle it can serve everything by itself. In practice two different setups exist, and confusing them is a common source of "why does it work for me but not in the test run?".

getAPIUrl is the function that hides this difference. It inspects window.location.hostname and picks the API base URL: localhost:8000 for local addresses, /api for the live domain, and the page's own origin otherwise.

4 · Inside the backend

Two files carry everything: server.rs at 1,262 lines and board.rs at 1,757 lines, of which roughly 900 are unit tests. The boxes below are groupings this document invented to make the file readable. They are not modules in the code — everything in the left column sits in one flat file.

The four maps are the thing to understand first

One game's state is spread across four independent maps, all keyed by the same match string:

MapHoldsWritten by
GAME_ROOMSThe board, both seats, the generation numberAlmost every handler
GUESS_STONESEach player's private guess markerssync_guess_stones
GROUPS_TO_REMOVEGroups clicked as dead during countingget_group
READY_TO_COUNTTwo booleans: has each player pressed Count scoreget_score, reset by get_group

The cost is visible in the cleanup handlers: reset_memory and remove_game clear GAME_ROOMS and GUESS_STONES but leave GROUPS_TO_REMOVE and READY_TO_COUNT untouched, so a deleted game leaves debris behind under its match string. Both handlers also use .unwrap() on the lock instead of the error-returning helpers, so a panic there poisons the lock for every other request.

5 · Inside the frontend

Six pages and seven JavaScript modules. There is no bundler and no framework — the browser loads the modules directly. Which page you are on is the identity model: getPlayerColor in utils.js reads window.location.pathname and returns black, white or spectator based on the filename.

Why the cycle exists, exactly

It is not one link, it is two, and they run in opposite directions:

  • script.js imports addingGuessStone and removingGuessStone from handlers.js. These are export let variables that handlers.js reassigns when the Guess stone button is clicked. JavaScript modules export a live binding, so script.js sees the new value without any event or callback — the update is invisible in the code.
  • handlers.js imports getDeadGroups from script.js, because the list of groups marked dead is stored in a variable that happens to live in script.js.

So the cycle is really shared mutable state with no owner. That matters for the refactor: moving the network calls out does not break it. Moving the state out does.

A correction worth making explicitly: elements.js calls getElementById while the module is being evaluated, but that is not a race with page loading — module scripts are deferred, so the DOM is already parsed. The nulls come from something simpler: one registry lists the union of elements across all pages, and black.html has no #main-board, main.html has no #undo-button, and so on. Every consumer therefore has to null-check.

6 · Where the hidden information actually lives

This is the part most worth reading carefully, because the code's naming suggests the opposite of what it does.

GameState has three board fields — board, black_player_board and white_player_board — which reads like the server produces one view per player. It does not. GameState::new assigns the same true board to all three, and no later code changes them. The frontend never reads the two per-player fields at all; every page uses data.board.

The consequence: the opponent's stone positions are present in the JSON response on every sync, so the browser holds information the player is not meant to have. The same is true of guess stones — each player's private markers are sent to both. Hiding is done by which SVG element is attached to the page, not by what the server sends.

The existing anti-cheating work guards a different thing, and guards it properly: validate_spectator_open and the ANTI-CHEATING comment stop a seated player from navigating to the spectator page to see both boards, and the end-to-end suite has two tests for exactly that. What is unguarded is the response payload, not the navigation.

Changing this changes what the server sends, so it is a behaviour change, not a refactor. It is kept out of the target architecture for that reason, and listed separately at the end of it.

7 · Runtime flows

Joining a game

The one-second polling loop

The generation number is incremented on both sides. The server bumps it on moves, passes, undos and guess-stone syncs. sendGuessStonesToBackend in the browser also bumps its local copy before sending, to avoid triggering its own refetch. The server file already carries a note about this: // TODO: analyze this handler usage for potentially incorrect generation number counting.

8 · Game phases

No field stores the phase. Every handler re-derives it: counting means last_two_moves_are_pass returns true, finished means get_winner returns something. That is why the phase checks are duplicated across handlers and why the browser has its own countingPhase and isWinnerDecided flags that can drift from the server's view.

The cleanup timer is only started from one place — get_score, after both players are ready. A game that ends by resignation, or that is simply abandoned, stays in memory until the process restarts or an admin deletes it.

10 · Structural problems

These are reasons the code is hard to read, not a bug list. Where something is also a defect, that is said plainly.

One game, four locks state

To answer "what is the state of game X" you must consult four maps. Two handlers that take the locks in different orders can deadlock, and the cleanup handlers already forget two of the four maps.

Move all four into GameRoom. One map, one lock, one place to look.

Two different ways of deciding who you are identity

cell_click, get_group and get_score derive the player from the session token through derive_player, which the code comments correctly describe as not trusting the client. But pass, undo, handle_resignation, should_sync and sync_boards take a plain player string straight from the request body and believe it. handle_resignation does not check a token at all, so a request can resign on another player's behalf.

One rule: derive the player from the token in one helper, at the edge, for every route. Delete the player field from the payloads.

server.rs is five files in one size

Routing, request shapes, response shapes, seat assignment, lock plumbing, admin tooling and static file serving share 1,262 lines with no boundary between "HTTP" and "what the game does".

Split along the groupings in diagram 4. Rust puts no ordering constraint on this — see the note at the start of section 11.

GameState answers every question at once coupling

Seventeen fields, returned by move, pass, undo, resign and sync alike. It is built by chaining with_guess_stones, with_winner and friends, so forgetting one call ships a placeholder instead of failing. Three fields describe boards but only one is ever read. Several handlers pass vec![] as the board because that response is not about the board at all.

One response type per phase. The compiler then tells you what each handler must fill in.

The placeholder is load-bearing protocol

GameState::new fills the dead-group field with a fake location at row 100, column 100. That value is not inert: toggleGroupSelection in UI.js checks if loc.row == 100 to tell "this came from the polling loop" apart from "the user just clicked a group". A magic number invented to fill a struct field became part of the wire protocol.

Send the two cases as two different things — for example an explicit field saying whether a toggle happened.

The sentinel border reaches the browser domain

Handlers add +1 to incoming coordinates and slice [1..=rows] on the way out. But the translation is not complete: get_group returns locations still carrying the offset, so UI.js subtracts 1 in two places, with the comment "The issue was with sentinels in the backend". An internal storage trick is now part of the API.

Give Board a public surface in real board coordinates and keep the padding private. Note this changes the wire format, so it is a late step.

The URL is the identity model frontend

getPlayerColor decides who you are by testing whether the path contains black.html. Four more places branch on pathname. black.html and white.html are 35-line near-duplicates. The server hard-codes those filenames in six redirect strings.

One board page, colour held in one module. Count the call sites first — six in the browser, six in the server.

Client state has no owner cycle

The import cycle described in section 5 is the symptom. The clearest illustration is deadGroupsDuringCounting: the polling loop assigns it a server object with a selected field, while the stone click handler assigns it the result of getGroupRequest — which returns nothing, because that function never returns its own promise. The same variable therefore holds two different shapes depending on which code path last touched it, and getDeadGroups reads .selected off whatever is there.

One state module that owns these variables and hands them out. The cycle disappears as a side effect.

Requests are issued from five places frontend

script.js, handlers.js, games.js, admin.js and an inline script inside index.html all call fetch directly, each with its own error handling, and two of them use the shared fetchWithErrorHandling wrapper while the rest do not. Nothing lists what this client can ask the server for. One consequence is already visible: removeGame sends no request body, while the handler expects a JSON object with a match string, so the admin delete button cannot work.

One module with one function per endpoint. It becomes the client-side contract, and the mismatch above becomes obvious.

One DOM registry for six different pages fragility

elements.js lists every element used anywhere, so on any given page most entries are null and every consumer guards. One entry is permanently dead: getElementById is given the CSS class selector ".main-board-buttons", which can never match an id. There is no visible symptom — the container is hidden by CSS, but handleGameButtonsAfterGame sets visibility on the buttons inside it, and a child can override a hidden parent. The end-to-end test for spectator counting controls passes. It is dead code that reads like live code.

Resolve elements per page, after deciding what that page needs.

Rooms mostly never go away lifecycle

Cleanup is scheduled from exactly one place, sixty seconds after a completed count. Resigned and abandoned games stay in memory until restart or a manual admin delete.

Give the room a last-touched timestamp — board.last_move_timestamp already exists and the admin list already uses it — and sweep on a timer.

Nothing is persisted by design, worth knowing

Every deploy ends every game in progress. The rejoin_required flag, the three-failure redirect and the "Game data lost" alert exist to soften that.

Not a defect. It explains why so much reconnect logic exists, and it is the reason a persistence layer would be a large change rather than a small one.

11 · Target shape, server side

Same routes, same polling protocol, same behaviour on screen. Only the boundaries move. Two constraints shaped this design, and they are worth knowing before you start:

  • Rust modules inside one crate may refer to each other freely. There is no import-cycle problem to design around, unlike in JavaScript. What you do have to plan for is visibility: methods that are private today, such as Board::get and Board::set, become invisible to a sibling module and need pub(crate). Splitting an impl Board block across several files is allowed and normal.
  • JavaScript modules must form a directed acyclic graph if you want each file to be readable alone. The browser-side design in section 12 is checked for that: every arrow points one way, and no path returns to its start.

How to think about each backend piece

PieceGive it exactly this jobThink about this while writing it
GameRoom Own every piece of one game's state, and expose methods rather than public fields. Do the merge first and change nothing else. Once the four maps are one struct, ask which of its current callers were only reaching in to read — those become methods on GameRoom, and the handler shrinks.
auth.rs Turn a token plus a match string into a Player or a spectator. One function, used by everything. Make the return type an enum, not a String. Today derive_player returns "black", "white" or "spectator" as text and callers compare strings; an enum makes the compiler check the match arms and kills the unreachable! in get_score.
play_service Apply a legal move to a room and report what changed. No JSON, no Json<T>, no status codes. The test for whether the split worked: can you call it from a plain #[test] without starting a server? If not, HTTP has leaked in. This is the layer that finally makes handler logic testable.
counting_service Own the whole end-of-game protocol: toggling dead groups, both ready flags, and the transition to scored. The rule that both ready flags reset whenever a group is toggled lives here, not in a handler. Right now it is a side effect buried in get_group and easy to miss.
response_builder Take a room plus who is asking, return the response type for the current phase. This replaces the with_guess_stones and with_winner chain. Prefer one constructor per phase over a builder with optional steps — a builder lets you forget a step, a constructor does not.
rooms.rs Hold the one global map, hand out guarded access, and run the sweeper. Keep the lock private to this module and expose something like with_room<F> that runs a closure while holding it. Callers then cannot hold a lock across an await, and lock ordering stops being something to remember.
rules.rs and friends Stay exactly as clean as board.rs is today. Move the matching #[cfg(test)] tests along with the code they cover. Do the split in one commit with no logic changes, so a failing test can only mean you moved something wrong.

12 · Target shape, browser side

How to think about each browser piece

PieceGive it exactly this jobThink about this while writing it
session.js Answer three questions: which match, which colour am I, what is my token. This is what replaces getPlayerColor reading the URL. Decide where the colour comes from before you merge the pages — either store it next to the token when joining, or ask validate-spectator on load, which already returns the colour for a token. Storing it is simpler; asking the server is harder to get out of sync.
api.js One exported function per endpoint, each taking real arguments and returning parsed data or throwing. Write it by reading the Rust payload structs, not the current JavaScript — that is how you catch mismatches like the one in removeGame. Let every function return its promise; the missing return in getGroupRequest is the bug this file design prevents.
gameState.js Hold the last known server state plus the UI flags, and notify subscribers when it changes. Move addingGuessStone, removingGuessStone and deadGroupsDuringCounting here first — that alone breaks the import cycle. Expose setter functions rather than mutable exports, so a change is something you can put a breakpoint on.
sync.js Run the loop, decide when to refetch, write results into gameState. Nothing else. It should not touch the DOM even once. If it needs to, the state model is missing a field. Keep the existing behaviour exactly — one second, three failures then rejoin — so this stays a refactor.
render/ Given a state object, produce the right SVG. Same input, same output, every time. Consider one renderer per board rather than the current shared updateBoard that removes every stone and rebuilds all three boards on each tick. Which stones a viewer may see becomes a decision made in one visible place — useful later if the payload issue in section 6 gets addressed.
controls.js Wire buttons to api.js calls and write results into state. Bind only the buttons the current page actually has. That is the natural moment to delete the null-guard on every element in elements.js.

13 · A safe order to do it in

Steps 1 to 6 keep the wire format identical, so the end-to-end suite should stay green throughout. Run it between every step; if it goes red, the previous step is where to look.

  1. Create gameState.js and move the three shared variables into it. This is what breaks the import cycle. Extracting api.js does not, which is worth knowing before you spend a day on it.
  2. Create api.js and move every fetch into it, including the inline one in index.html. Read the Rust structs while you do it.
  3. Merge the four maps into GameRoom and delete three of the four lock helpers. Pure state consolidation, no logic change.
  4. Unify identity: route every handler through one token-based lookup and delete the player field from request payloads. This closes the resignation gap. It changes what the server accepts, so the browser must stop sending that field in the same commit.
  5. Split server.rs into the modules in diagram 11. File moves and visibility changes only.
  6. Split board.rs into rules, scoring, SGF and types, moving the unit tests with their code.
  7. Merge black.html and white.html into board.html and introduce session.js. Twelve call sites move: six pathname checks in the browser, six hard-coded redirect strings in the server. Two end-to-end helpers also check pathname and will need updating — that is expected, not a regression.
  8. Split GameState into per-phase responses and remove the row-100 placeholder. This changes the wire format in both directions, so it goes last, with the browser change in the same commit.
  9. Remove the sentinel offset from the API, so UI.js stops subtracting 1. Also a wire-format change; it pairs naturally with step 8.

Deliberately not in the target architecture

These are real improvements, but each changes what the program does, so none of them belong in a refactor that is supposed to be invisible. Do them as their own pieces of work, with their own tests:

  • Send each player only their own view. Section 6. Once response_builder exists and takes "who is asking" as an argument, this becomes a change in one function rather than a change everywhere.
  • Put a password on the admin routes. The author's TODO in admin.js already says so.
  • Restrict the SGF export. send_game_record returns the full move record for any match string, including for a game still in progress.
  • Sweep abandoned rooms. Needs a decision about how long is too long, which is a product question rather than a structural one.
  • Replace polling with server-sent events. Worth considering only after sync.js and api.js exist, because then it is one file that changes.
